# Internacionalização (i18n)

O app detecta o idioma do dispositivo automaticamente — tanto em nativo (iOS/Android) quanto na web (desktop/mobile) — e permite ao usuário sobrepor manualmente essa escolha em Configurações. Este documento registra as decisões tomadas e por quê, para quem for estender a tradução a novas telas ou novos idiomas.

## Stack escolhida

- **`expo-localization`** para ler o idioma do dispositivo (`useLocales()`). É o pacote oficial do Expo, funciona igual em nativo e web (na web lê `navigator.languages` por baixo dos panos) e é reativo: se o usuário troca o idioma do SO com o app aberto, o app acompanha em tempo real sem precisar reiniciar.
- **`i18next` + `react-i18next`** para gerenciar as traduções. É o padrão de facto do ecossistema React/React Native (também é o que o `expo-router`/comunidade Expo recomendam), tem suporte maduro a interpolação/plural e o hook `useTranslation()` já re-renderiza automaticamente quando o idioma muda.
- Traduções são **JSON estático embutido no bundle** (`locales/pt-BR.json`, `locales/en.json`), não hospedado remotamente. Para os 2 idiomas que o app tem hoje isso é suficiente e evita uma dependência de rede/flicker de "carregando tradução" — mesma filosofia de simplicidade do resto do `lib/` (ver `lib/theme.tsx`, sem dependência externa nem servidor de config).

Por que não `expo-localization` sozinho (sem i18next)? Interpolação, fallback e re-render automático por idioma já vêm prontos no i18next; reimplementar isso à mão não valeria a pena para um app com 2 idiomas hoje e a possibilidade real de crescer.

## Arquitetura (`lib/i18n.tsx`)

Espelha o padrão já usado por `lib/theme.tsx` (`ThemeProvider`/`useTheme`/`useThemeMode`) de propósito, para manter os dois sistemas de preferência do usuário (tema e idioma) com a mesma forma:

- `I18nProvider` — no topo da árvore em `app/_layout.tsx` (antes até do `ThemeProvider`, pois é o provider mais "global"). Resolve o idioma ativo a partir de duas fontes:
  1. **Preferência salva** (`daqui.language` no `lib/storage.ts`, mesmo padrão de `daqui.theme`): `'auto'` (padrão) ou um idioma fixado manualmente (`'pt'` | `'en'`).
  2. Quando a preferência é `'auto'`, o idioma vem do primeiro locale do dispositivo (`useLocales()`) que bate com um dos idiomas suportados — comparando só a subtag de idioma (`en-US` → `en`), ignorando região. Se nenhum bater, cai no fallback `pt` (mercado de origem do Daqui).
- `useLanguage()` — expõe `{ language, preference, setPreference }` para a UI de configurações (`app/settings.tsx`).
- `useT()` — reexporta `useTranslation` do `react-i18next`; use `const { t } = useT();` em qualquer componente sob o `I18nProvider`.
- Ao trocar de idioma, também atualiza `document.documentElement.lang` na web (só existe lá) — sinal usado por leitores de tela e SEO.

### Por que oferecer override manual, e não só seguir o dispositivo

"Auto" é o padrão porque é a expectativa da maioria (Apple HIG e Material Design recomendam explicitamente detectar o idioma do sistema). Mas as duas plataformas também recomendam deixar o usuário sobrepor isso dentro do próprio app — cobre o caso de dispositivo compartilhado/emprestado, ou de alguém que só prefere usar o app num idioma diferente do resto do sistema. Por isso `Configurações → Aparência → Idioma` tem as 3 opções (Automático / Português / English), reaproveitando a mesma seção visual do toggle de tema claro/escuro.

## Idiomas suportados hoje

`pt` (padrão/fallback) e `en`. Para adicionar um novo idioma:
1. Criar `locales/<code>.json` com exatamente as mesmas chaves de `locales/pt-BR.json`.
2. Registrar `<code>` em `SUPPORTED_LANGUAGES` e no `resources` de `lib/i18n.tsx`.
3. Adicionar as 3 traduções do próprio seletor em `settings.language.<code>` nos dois arquivos JSON existentes.

## Escopo coberto nesta primeira leva

Dado o tamanho do app (~130 arquivos de tela/componente, a esmagadora maioria com texto em português hardcoded), traduzir cada string de cada tela seria um projeto à parte. Esta primeira leva prioriza a **infraestrutura completa e correta** + as superfícies de **maior visibilidade e mais visitadas por um usuário ainda deslogado** (onde o idioma do dispositivo é o único sinal disponível, já que não há preferência de conta ainda):

- Navegação: tab bar mobile (`app/(tabs)/_layout.tsx`), sidebar desktop e drawer mobile (`components/LeftSidebar.tsx`, reaproveitado por `components/MobileMenu.tsx`).
- Fluxo de autenticação completo: `app/(auth)/welcome.tsx` (hero + login + cadastro embutidos, versão desktop), `login.tsx`, `signup.tsx`, `forgot-password.tsx`, `reset-password.tsx`, `google-username.tsx` — inclusive as mensagens de validação client-side em `lib/useLoginFlow.ts`/`lib/useSignupFlow.ts`.
- `app/settings.tsx`: só a seção "Aparência" (tema + o próprio seletor de idioma) foi traduzida; as demais 4 seções (perfil, privacidade, notificações, endereço) permanecem em português.

**Fora do escopo, por decisão consciente:**
- O restante das ~120 telas/componentes do app (feed, posts, comentários, mensagens, grupos, mapa, anúncios, etc.) continua com texto fixo em português. O padrão para estender está estabelecido (ver "Como traduzir uma tela nova" abaixo) — é trabalho mecânico de replicar, não uma decisão de arquitetura em aberto.
- **Conteúdo dinâmico vindo do backend** (texto de posts/comentários escritos pelos próprios usuários, nomes de categoria, mensagens de erro de validação da API) não é e não deveria ser traduzido por este mecanismo — são dados, não strings de UI. Localizar respostas de erro da API exigiria i18n no `backend/` (e no `ads-backend/`) também, o que é um projeto à parte, fora do escopo de uma mudança só de frontend.
- Formatação de data/hora (`lib/time.ts`) e de número (`toLocaleString`) fora dos arquivos tocados aqui continuam fixas em `pt-BR`.

## Como traduzir uma tela nova

1. `import { useT } from '../lib/i18n';` e, no componente, `const { t } = useT();`.
2. Adicionar as chaves novas em **ambos** `locales/pt-BR.json` e `locales/en.json`, sob um namespace com o nome da tela/feature (siga o padrão já usado: `nav.*`, `auth.*`, `settings.*`).
3. Trocar a string literal por `{t('namespace.chave')}` (ou `t('namespace.chave')` quando for `placeholder`/`label`/parâmetro de função, não filho de JSX).
4. Rodar `npx tsc --noEmit` — como as chaves são strings simples (não tipadas contra o JSON), erros de chave errada só aparecem em runtime (texto cru tipo `namespace.chave` na tela) ou visualmente; não há checagem estática de que uma chave existe nos dois arquivos.
